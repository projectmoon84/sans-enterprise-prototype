Design fidelity and flow review

The 16 original frames in the linked Admin user management section were inventoried and used to rebuild the prototype’s layout, components and flow states. This report records coverage, corrections, evidence and the places where the source does not define a complete product rule.

Open packaged prototype · Developer coverage data · Original Figma section

Assessment: The original prototype’s main fidelity gaps have been corrected. Every one of the 16 supplied frames has a corresponding route or state. This is a measured visual/behavioural review, not a pixel-diff certification. Source illustration data and dynamic mock data differ, and browser rendering can introduce small variations.

Method and independent review

The review used original frame exports, Figma layout measurements, browser screenshots and real interactions. A separate design reviewer inspected all 16 references and identified layout/component gaps. A second reviewer exercised the flows and mock data. Their findings were consolidated into implementation changes, followed by targeted desktop and narrow-screen confirmation. The source Figma file was left unchanged.

Review criteria: layout hierarchy and alignment; typography and colour; control sizing and states; table structure and density; dialog composition; confirmation and cancellation; draft preservation; validation and recovery; persistence; and separation between defined source behaviour and prototype assumptions.

Most significant corrections

  • Shell and lists: restored the original SANS vector mark and bundled Fira Sans; measured sidebar/topbar, navigation hierarchy, page offsets, card placement, toolbar widths, table columns and row density. Removed extra introductory decoration and moved demo utilities into the profile menu.
  • Portal invitations: removed the extra name field; restored role/scope sections, All Groups, searches, Select all, counts and Summary composition. Required selections and confirmation gate sending; returning from review preserves choices.
  • Individual students: restored email/voucher/Sub-org/team columns, saved rows, edit/delete, numbered entries and assignment reuse. Fixed unsaved-row review and discard-dialog paths that could lose a draft. Added timed sending, partial results and retry.
  • CSV: restored all four upload states, explicit Continue, staged review, warnings and inline assignment pickers. Fixed a picker class-list exception. Corrected error counts so malformed emails are not counted as account lookup failures.
  • Components: aligned primary buttons, steppers, selection/indeterminate checkboxes, select arrows, status pills, search fields, kebabs, warning panels and success dialog composition.

Final visual evidence

Behaviour and validation evidence

  • Portal creation, role-dependent summaries, required confirmation, pending status, editing scopes, live search and persistence after reload were exercised.
  • The independent behaviour pass exercised All Groups; voucher/team search; Select all; review/back preservation; manual student Save, Add Another, reuse, edit and delete; unsaved-draft blocking; discard cancellation; and partial send/retry.
  • CSV sample: intermediate progress, 100% Ready, disabled/enabled Continue, remove file, staged review, validation, row correction, searchable assignment selection and valid-row completion were exercised. Native OS drag-and-drop was not directly tested.
  • A 390 × 844 viewport check confirmed the adapted list and tall invitation dialog: the table scrolls within its wrapper and the invitation action footer remains visible. No mobile Figma reference exists in this section.
  • Six automated data tests cover seed integrity, CSV quoting/BOM/CRLF/newlines, malformed CSV, duplicate/email/assignment validation, custom teams and invalid database imports. JavaScript syntax and standalone build checks pass.
  • The Impeccable source detector returned zero findings. This is a design-pattern check, not a guarantee of visual fidelity or runtime correctness.
  • The package contains embedded scripts, styles, fonts and logo; editable developer sources; the sample CSV; this review and reference images. Archive integrity is checked. HTTP browser behaviour was tested; direct file opening and both platform launcher GUIs were not exercised by automation.

Explicit differences and product decisions

  • Permission matrix: the source labels a role Admin while describing read-only abilities. The app uses role-dependent demo permissions. Production permissions still require a product decision.
  • Voucher scope: source copy says vouchers are filtered by Admin Groups but no voucher-to-group mapping is defined. All four demo vouchers remain selectable; the app does not invent that policy.
  • Mock account lookup: deterministic failure fixtures reproduce account-not-found and partial-send states. There is no external SANS account lookup. The supplied sample has one ready and three invalid rows on a fresh database; counts change with edits and duplicates.
  • Dynamic content: people counts, assignments, validation totals, invitations and row heights respond to the mock data. Source review/result illustrations show inconsistent student counts. The prototype keeps actual counts consistent.
  • CSV columns: some source examples place team and Sub-org values under inconsistent headings. The app assigns values according to the field’s meaning.
  • Results: “Sending” becomes a completed partial/full result when local timers finish. The source combines completed and in-progress labels.
  • Terms and invitations: the terms control opens a prototype placeholder because no legal content was supplied. Invitation-list navigation uses the Students pending filter because no separate invitations screen is included.
  • Additional views: Home, Learning, Account & Finance, directories, general edit dialogs, data utilities and work-role picking are supporting prototype additions. Their appearance cannot be certified against this section’s 16 frames.
  • Storage: existing edited/imported data is preserved. Only untouched initial fixtures receive the reference-data refresh. Each browser has its own local database; the zip never includes the author’s browser data.
